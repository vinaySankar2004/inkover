# Writing rules

These apply to every markdown file in the repo. They exist so the docs stay small enough to load and true enough to trust.

## One home per fact

| Kind of fact | Its only home |
|---|---|
| Why we chose something | A decision file |
| What the user experiences | A feature spec |
| How it works under the hood | `docs/architecture.md` |
| What a word means | The glossary in `docs/product.md` |
| What is out of scope | Non-goals in `docs/product.md` |

If a sentence would be true in two files, write it in the one above and link from the other. A link is `[[slug]]` or, for architecture, the heading name in prose: "see architecture, Anchoring."

## Verbosity budget

- Purpose: at most three sentences.
- Behaviour rule: at most 30 words. If it needs more, it is two rules.
- Edge case row: one situation, one expected outcome.
- Decision file: under 25 lines total.
- Architecture section: under 40 lines. Split by mechanism, not by feature.
- No history in specs. A spec describes the present. Changes are visible in git and in decisions.
- No hedging words: "should", "probably", "might" do not appear in a spec at `specified` or later.

## Freshness

- Every doc carries `updated:`. Change it whenever the body changes.
- Behaviour changes edit the spec and the code in the same commit. The commit message names the spec.
- `docs/index.md` is regenerated by `scripts/build-index.py`, which also reports broken wikilinks. Run it before reporting status and before any commit that touches `docs/`.
- When code is found doing something a spec does not say, that is a bug in one of them. Decide which, fix it, same day.

## Voice

Plain, direct, present tense. "The Pencil is captured." Not "The Pencil will be captured by the system." Use glossary terms exactly. Numbers go in tables, not sentences.

## Banned

These read as machine-written and are not used anywhere in the repo, including commit messages, code comments and the README.

- Em dashes and en dashes. Use a comma, a colon, or a new sentence.
- Arrows in prose. Write "then" or "becomes".
- Emoji, exclamation marks, rhetorical questions.
- Filler openers: "In today's", "It's worth noting", "Let's dive in", "Simply", "Seamlessly".
- Inflated adjectives: robust, powerful, seamless, cutting-edge, comprehensive, elegant.
- Lists of three for rhythm when there are two or four real items.
- Restating the heading as the first sentence under it.
- Summaries at the end of a section that repeat the section.
