# Inkover

Safari Web Extension for iPadOS. Apple Pencil draws over any web page; a finger keeps browsing. A personal reading aid for one user.

Built on ICM: the docs are the source of truth, the code implements them, and the folder structure routes you. Anything learned goes into a file, never into memory alone.

## Where things live

| Path | Holds |
|---|---|
| `README.md`, `CONTRIBUTING.md` | The human entry for GitHub visitors: install steps, how to contribute. Agents start here instead. |
| `docs/product.md` | What Inkover is, non-goals, glossary. Always load. |
| `docs/architecture.md` | The mechanisms every feature shares. Load when touching code. |
| `docs/features/` | One spec per feature: behaviour, edge cases, acceptance. |
| `docs/decisions/` | One file per decision, numbered, with the why. |
| `docs/index.md` | GENERATED status board. Rebuild with the script, never edit. |
| `docs/store/` | App Store: market analysis, the exact listing text, the release procedure. |
| `docs/privacy.md` | The privacy policy the App Store links to. Published by GitHub Pages. |
| `index.md`, `support.md`, `_layouts/`, `assets/` | The public site: landing page, support page, shared layout and styles. GitHub Pages builds it from `main`. |
| `_meta/` | Schema, writing rules, templates. The factory. |
| `extension/` | The web extension source. The only home for code. |
| `dev/` | Harness page that runs the content script in a desktop browser, mouse as Pencil. Serve the repo root and open `dev/harness.html`. |
| `Inkover/` | Xcode wrapper generated by Apple's converter. No logic lives here. |
| `scripts/` | Rebuilders for generated files. |

## Route by task

| If | Read | Then |
|---|---|---|
| Any task | `docs/product.md` | Continue with the row that matches. |
| Proposing a feature | `_meta/feature-template.md` | Copy into `docs/features/` with `status: proposed`. |
| Making a call | `_meta/decision-template.md` | Write `docs/decisions/DNNNN-slug.md`, link it from the affected spec. |
| Implementing a feature | Its spec, `docs/architecture.md`, `CONTEXT.md` | Code in `extension/`, then set `status: built`. |
| Verifying a feature | The spec's Acceptance list | Run it on the iPad, tick the boxes, set `status: verified`. |
| Changing behaviour | The spec first | Edit the spec, then the code, in the same commit. |
| Asked for status | Run `python3 scripts/build-index.py` | Read `docs/index.md` and report. |
| Shipping a release | `docs/store/release.md` | Follow it top to bottom. Listing text comes from `docs/store/listing.md`, never retyped. |
| Changing price or store copy | `docs/store/listing.md` first | Then App Store Connect, same day. |
| Writing any doc | `_meta/writing-rules.md` | Follow it. |

## The rules that matter most

- One home per fact. Why lives in a decision, what in a feature spec, how in architecture. Link, never copy.
- A spec that disagrees with the code is a bug. Fix one of them the same day.
- Nothing reaches `status: built` until a human has read the spec at `status: specified`.
- Do not load the whole `docs/` tree for a task. Load product, the one spec, and what it links to.
